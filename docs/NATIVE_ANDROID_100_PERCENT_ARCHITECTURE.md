# CpiPOS Native POS 2.0 — ข้อกำหนดสถาปัตยกรรมหลัก (22 ต.ค. 2026)

> **ข้อกำหนดที่ยืนยันโดยเจ้าของผลิตภัณฑ์:** Native 2.0 เป็นแอป POS สำหรับ **โทรศัพท์มือถือ Android แบบ Native 100%** ไม่ใช่แอปครอบเว็บ ไม่ใช่ WebView, PWA, TWA หรือเว็บไซต์ที่เปิดภายในแอป และต้องใช้ระบบธุรกิจ/ฐานข้อมูล **CpiPOS-001 เดียวกับ POS ฝั่งแท็บเล็ต** โดยไม่แยกข้อมูลร้าน สต๊อก หรือยอดขาย

## ขอบเขตที่ไม่เปลี่ยน

- **Presentation และ UX:** Kotlin + Jetpack Compose, Android Activity, Native Navigation และ UI สำหรับจอมือถือโดยตรง ตั้งแต่ล็อกอิน เลือกสาขา รหัสพนักงาน เลือกเครื่อง หน้าขาย ตะกร้า ชำระเงิน ใบเสร็จ ไปจนถึงระบบสแกนและจัดการอุปกรณ์
- **ห้ามใช้ WebView เพื่อแสดง POS หรืออาศัย HTML/JavaScript เป็นตัวขับหน้าขาย.** การอ้างชื่อเดิม `WebPosClient` หมายถึงคลาส Kotlin ที่เรียก HTTPS JSON API เท่านั้น **ไม่ใช่ตัวแสดงเว็บ**. หากต้องปรับชื่อในอนาคตควรทำเป็น refactor ที่มี Test กำกับ ไม่ใช่เปลี่ยนพร้อมระบบชำระเงิน
- **ใช้ข้อมูลธุรกิจเดียวกันกับ POS ฝั่งแท็บเล็ต:** Tenant, Branch, User, Devices, Products, Prices, Inventory, Permissions, Shifts, Orders, Payments, Receipts, Package Entitlements อยู่ภายใต้สัญญา API และฐานข้อมูล Supabase **CpiPOS-001** เดียวกัน
- **Backend/API ไม่ใช่ WebView:** แอปมือถือสามารถเรียก Backend ผ่าน HTTPS แบบ Native เพื่อเข้าสู่ระบบ ตรวจสิทธิ์ อ่านข้อมูล และสร้างคำสั่งขายที่ตรวจสอบสิทธิ์แล้วได้เหมือนแท็บเล็ต ปัจจุบันใช้ API จาก `https://cp-ipos-web.vercel.app` เป็นช่องทางเข้าถึงธุรกิจเดียวกัน ไม่ได้นำหน้าเว็บจาก URL นั้นมาแสดงบนมือถือ
- **ความปลอดภัยข้อมูล:** ห้ามใส่ `service_role`, database connection string, employee PIN, cookie ส่วนตัว, หรือคีย์ลับลงใน APK; ห้ามอนุญาตให้ Native แก้ยอดขาย สต๊อก สิทธิ์ร้าน หรือการรับเงินโดยข้ามการยืนยันจากเซิร์ฟเวอร์
- **มือถือไม่จำเป็นต้องมี Backend หรือฐานข้อมูลแยก:** ไม่สร้าง Supabase ใหม่เพื่อ Native, ไม่แยกยอดขายกับแท็บเล็ต และไม่ใช้อีเมล/บัญชีลูกค้าคนละระบบโดยไม่มีเหตุจำเป็น
- **Offline:** หน้า UI เป็น Native 100% แม้ยังไม่มี Offline Sync ครบวงจร นั่นเป็น *ความสามารถที่ยังพัฒนาไม่เสร็จ* ไม่ใช่เหตุผลให้เปลี่ยนไปใช้ WebView; การขายออฟไลน์ต้องมีกลไก queue/idempotency/การยืนยันและซิงก์ยอดอย่างปลอดภัยก่อนเปิดจริง

## แผนแยกชั้น (Target Architecture)

```text
Android Phone: Native 2.0                 Tablet POS
Kotlin / Jetpack Compose UI                Existing POS UI
Native UI + local state + device I/O       Tablet workflows
             |                                 |
             +---------- HTTPS JSON API -------+
                              |
                Auth / Tenant / Branch / Rules
                Validation / Transaction / RPC
                              |
                 Supabase CpiPOS-001 (Primary)
            ร้าน / สินค้า / สต๊อก / กะ / ออเดอร์ / รับเงิน
```

> อุปกรณ์ทั้งสองใช้ **ข้อมูลชุดเดียวกัน** แต่การจัดวางหน้าจอและปุ่มต้องเหมาะกับจอและระบบปฏิบัติการของแต่ละอุปกรณ์ ไม่ใช่ย่อหน้าแท็บเล็ตมาใส่โทรศัพท์

## ลำดับงาน Native ที่ต้องพัฒนาต่อ

1. รักษาหน้าจอ Native และโฟลว์ต้นฉบับ: Store Code → สาขา → PIN พนักงาน → เครื่องขาย → กะ → โหมดขาย; **ไม่มีหน้าเว็บซ้อนหรือปุ่มทดลอง UI**
2. ยืนยัน Endpoint, Auth Session, Device Binding, สิทธิ์ Store/Branch/User และ Package ตรงกับ Tablet POS; ตรวจ Boundary ของทุก Endpoint แบบข้ามร้าน
3. รายการขายต้องเป็นข้อมูลกลางเดียวกัน: ราคาล่าสุด/สต๊อก/โปรโมชัน/ภาษี/ส่วนลด/ใบเสร็จ ผ่าน Backend; ตัวแอปไม่แต่งยอดเงินสำเร็จเอง
4. ปิดงาน P0: บันทึกเงินสดที่รับจริงและเงินทอนในฝั่งเซิร์ฟเวอร์; กู้คืนบิลค้าง/ผลลัพธ์ไม่แน่นอนโดยอ้างอิงเลขคำขอเดิม และห้ามตัดสต๊อก/ตัดเงินซ้ำ
5. พัฒนา Native UI สำหรับฟังก์ชันร้านค้า/ร้านอาหารตามสิทธิ์แพ็กเกจ รวมระบบกล้องสแกนบาร์โค้ด, การพิมพ์ ESC/POS, Bluetooth/USB/เครือข่าย, รองรับสกุลเงิน THB/LAK/USD; ห้ามอ้างว่าครบก่อนทดสอบจริง
6. เพิ่มการทำงานออฟไลน์และ Sync ผ่าน local database + คิวที่มี idempotency / conflict handling ก่อนเปิดการขายออฟไลน์จริง
7. ทดสอบไฟล์ APK Debug บน Android จริงผ่าน VS Code/Gradle/ADB โดยใช้ร้านและเครื่อง QA ที่ได้รับอนุมัติ ตรวจทั้งหน้าจอแนวตั้งและการหมุนจอ ความละเอียด ฟอนต์ไทย ปุ่มกด ความหน่วง และการเชื่อมต่อ

## สถานะยืนยันล่าสุด

- โค้ดเปิดแอป `MainActivity` ใช้ `setContent { MobilePosLiveScreen(...) }` กับ Jetpack Compose จริง
- `app/src/main/AndroidManifest.xml` เปิด Android `MainActivity` เป็น Launcher และไม่เปิด WebView
- ไม่มีไฟล์หน้าเว็บ/PWA/HTML ในต้นไม้ไฟล์ของ Branch Native ที่ตรวจสอบ
- งาน Offline, Printer Hardware, Mobile Device UAT, Multi-Currency และการคืนสถานะ Payment ยังไม่ครบ; ข้อกำหนดนี้เป็น **เป้าหมายสถาปัตยกรรม** ไม่ได้หมายความว่าฟีเจอร์ทุกตัวเสร็จแล้ว

## ขอบเขตการเปลี่ยนแปลงรอบนี้

เอกสารนี้ยืนยันสถาปัตยกรรมสำหรับทีมพัฒนาต่อ **ไม่เปลี่ยน API, ฐานข้อมูล Production, ฟีเจอร์ที่มีอยู่, Device Binding หรือการรับเงินจริง** และไม่อนุมัติการ Merge เข้า `main` หรือเปิดขาย Native 2.0 ให้ลูกค้าก่อนผ่าน UAT.
